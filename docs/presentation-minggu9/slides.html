Mengapa Ubuntu Server

  • Replika benar-benar menyerupai backend IoT (nginx, MariaDB, Mosquitto)

05 · Live Demo Singkat

Security Onion memantau traffic lab

Demo di layar, ±3 menit — traffic uji, bukan serangan sungguhan.

Yang ditunjukkan

  1. Alerts & Hunt — Security Onion menerima log dari sensor
  2. Zeek conn.log — pasangan IP Attacker ↔ Target terlihat
  3. tcpdump di sensor — bukti paket nyata, bukan simulasi
  4. Grid / Kibana — ringkasan trafik per host

Kalau demo gagal di kelas

  • Screenshot ber-timestamp disimpan di repo sebelum sesi
  • File baseline_minggu9.pcap dibuka ulang di Wireshark
  • Fokus beralih ke penjelasan rule alert yang akan dipakai Fase 2

Prinsip Bagian III panduan: target adalah VM replika di jaringan tertutup — tidak ada pengujian ke sistem Mitra.

Perintah demo (ringkas)

sudo tcpdump -i eth0 -nn host 192.168.4.5 && ping -c 5 192.168.4.5
ssh iotadmin@192.168.4.5 "sudo ss -tulpn"  |  nmap -sV 192.168.4.5
# Security Onion → Hunt → query: event.dataset:conn source.ip:192.168.4.100

06 · Attack Plan Fase 2

5 skenario, 4 kategori, tools sudah dikunci

Setiap skenario tertuju ke Target Node replika dan berakar pada celah hasil riset Minggu 4.

IDKategoriTeknik & tools Target / celah acuanDeteksi diharapkan
RT-01Reconnaissance Full TCP scan, service/OS fingerprint · nmap 192.168.4.5 (semua port) Zeek Port_Scan / ET SCAN
RT-02Exploitation Brute-force kredensial lemah → shell + sudo · Hydra, Metasploit :22 user iotadmin (→ :2222) auth.log Failed→Accepted, Zeek
RT-03Web / API SQL injection pada endpoint data sensor · sqlmap, Burp http://192.168.4.5/iot-dashboard/ ET WEB_SERVER SQLi, Zeek http.log
RT-04Protokol IoT MQTT spoof publish ke topik aktuator · mosquitto_pub, MQTT Explorer :1883 broker tanpa auth kondisional Rule kustom (belum ada bawaan)
RT-05Availability maks. 1 SYN flood 60 detik · hping3 :80 dashboard ET DOS, Zeek conn.log (S0)

Kenapa rencana ini sah

Semua tools disebut sejak awal (bukan saat eksekusi), tiap skenario punya kontrol mitigasi pasangan di checklist — jadi Blue Team bisa siapkan deteksi lebih dulu.

Batas yang kami patuhi

Hanya 192.168.4.0/24; DoS ≤60 detik satu service; snapshot sebelum tiap sesi; tidak menyentuh sistem Mitra.

Siklus tertutup

Tiap serangan diuji ulang setelah mitigasi. Yang dinilai bukan rumitnya serangan, tapi bukti bahwa serangan yang sama kini gagal.

07 · Kendala & Pembelajaran

Yang menghambat, dan langkah berikutnya

Kendala

Target generik vs tuntutan IoTTarget diganti ke Ubuntu Server; kelemahan dipasang sengaja agar skenario tetap punya sasaran
RAM laptop3 VM tidak bisa jalan bersamaan → Security Onion dijadwalkan bergantian

Deteksi MQTTTidak ada signature bawaan → harus tulis rule kustom

Pembelajaran

  • Hardening harus tiga lapis (akses, permukaan serangan, data/aplikasi) — satu layer tidak cukup
  • Tanpa baseline normal, alert tidak bisa dinilai "benar" atau "noise"
  • Rencana serangan yang tool-nya jelas membuat deteksi bisa disiapkan paralel, bukan reaktif
  • Celah paling berbahaya di backend IoT sering berupa default credential & broker tanpa auth, bukan exploit rumit
